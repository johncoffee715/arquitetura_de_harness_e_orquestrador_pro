# Qwen3.8-27B on 6GB VRAM: Bonsai 27B is HERE!

---
A full 27 billion parameter language model fitting inside a 6 GB file while matching 98% of its full precision score sounds like marketing fiction until you inspect the weight matrices. Prisml released Turner Bonsai 227B taking Quen 3.827B and compressing the language backbone down to 1.7 bits per weight using turnary values and hadomard rotations. that theoretically lets you run a 27Bclass model on an RTX 3060 12 gig or an entry-level Mac with unified memory. But well, before you swap out your daily local coding setup, the actual hardware demands and benchmark drops tell a much more grounded story. So what is Bonsai 227B? Under the hood, the base architecture matches Quen 3.827B, you have 27.36 billion total parameters. The language backbone has 24.35 billion parameters across 64 blocks. The embedding and output head take 2.54 billion and the separate vision tower takes about 0.47 billion parameters across 27 blocks. It uses a hybrid attention setup where roughly 75% of the layers use linear attention and 25% use full attention along with swigloo activations and RMS norm. The core engineering here is the turnary quantization. In standard FP16, each parameter takes 16 bits. Bonsai 227B maps language model matrix weights to three values, minus1, 0, or + one. Information theory tells us that a turnary state carries log base 2 of three or roughly 1.585 bits of information. Prism ML groups every 128 weights together and assigns them a single FP16 scale factor. 16 bits spread across 128 weights adds 0.125 bits per parameter, bringing the rate to about 1.71 bits per weight. A tiny fraction of the language model stays in higher precision. Specifically, 26.2 2 million parameters which is less than a tenth of a percent of the model remain in BF-16 to protect sensitive layers like normalization weights and the recurrent states in the linear attention path that nudges the true average to 1.72 bits per weight in theory and about 1.76 bits inside the packaged file to make turnary quantization work without destroying output quality. Prism ML uses a blockwise Walsh had rotation with a block size of 1,024. In plain English, large activation spikes usually blow out low bit quantization grids. Folding a hadomard rotation directly into the stored weights spreads those outlier spikes evenly across the entire block. The catch is that during inference, the runtime has to apply a sign flip and a fast hadomard transform to input activations before the matrix multiply. That activation rotation adds real compute overhead to batch one decoding. So it is a direct trade between memory footprint and mathematical operations. The weights also stay packed in memory. Custom kernels unpack turnary values on the fly during matrix multiplication. If the engine had to decompress weights back into FP16 in VRAM, the entire memory saving would disappear. When you look at the hugging face repository, there are two primary GGUF files. The smallest release is PTQ10 measuring 5.93 GB. The second format is PQ2020 at 7.2 GB which sits at roughly 2.16 bits per weight. The vision projector comes separately with a compact Q80 version taking 0.63 GB and a reference BF16 version taking 0.93 GB. For Apple silicon users, there is also an MLX package that takes 8.6 6 GB. Because the generic MLX low bit container stores both a scale and a bias per group, choosing between PTQ10 and PQ20 comes down to your hardware bottleneck. PTQ10 moves 18% less data over the memory bus, which gives you faster token generation on memory bandwidth constrained consumer cards like an RTX 4060 or an RTX 4090. But unpacking those dense trits requires more arithmetic cycles. PQ20 needs less compute to unpack. So prompt processing or prefill runs faster on highMP compute hardware like the RTX5090. There is a major runtime trap you need to know about. You cannot run these weights on stock Llama CPP. If you take the development Q20 file and load it into vanilla Llama CPP, the engine loads it without errors, skips the required activation transform, and outputs complete garbage. To run Bonsai 227B today, you have to use Prism ML's custom fork of Llama CPP or their MLX runtime. The weight file itself sits at 6 GB, but context memory does not come free. Because of the hybrid attention architecture, the FP16 KV cache consumes roughly 64 kilob per token. Let's look at the actual numbers. At 4K context, the KV cache takes about 0.25 GB of VRAM. At 10K context, that climbs to 0.63 63 GB. At 100K context, you need 6.1 GB of VRAM just for the KV cache. At the full 262K context, the KV cache alone demands roughly 16 GB of VRAM. Add 5.9 GB of model weights, 16 GB of KV cache, and 1.2 GB of runtime overhead, and you are looking at over 23 GB of allocated VRAM. If you have an RTX 4070Ti Super with 16 GB of VRAM or a 16 GB laptop, you cannot run full context in FP16.
